# Talk Track Builder

Build practical talk tracks that help sellers run clearer, more outcome-focused conversations.

## Confirm Inputs First

- Use supplied current context or relevant sections of `.enablement/context.md` when available. Treat stale, inferred, or conflicted material as provisional; never update shared context silently.
- Confirm audience role and seniority (AE, SDR, SE, manager).
- Confirm persona and buying stage.
- Confirm use case or commercial motion.
- Confirm channel and interaction type, total meeting duration, available speaking time, synchronous or recorded delivery, and any required handoff.
- Confirm core value message and approved proof sources, including claim owner and as-of date when available.
- Confirm top objections or risk themes expected in the conversation.
- Confirm desired call outcome and next-step ask.
- If inputs are incomplete, ask for only the minimum missing items. Use labeled assumptions only for reversible conversation structure or diagnostic hypotheses; keep source facts, proof, pricing, capabilities, approvals, and customer claims unknown until verified.

## Read The Right Reference

- Read [references/talk-track-framework.md](references/talk-track-framework.md) before drafting tracks; use it for structure, branch logic, and stage-specific variants.

## Default Workflow

1. Start with one call objective.
Pick one outcome for the call and one concrete next step you want the buyer to agree to.
2. Pull the best source material.
Use the value proposition, objection library, battlecard, customer evidence, and recent release notes if they help. Trace every proof statement to a source that supports the stated audience, use case, and scope; label directional evidence and omit unsupported claims.
3. Choose the track type and time budget.
Pick the defined conversation moment within discovery, demo, commercial, renewal, expansion, or manager coaching. Allocate time by beat and include only the spoken components that serve it. If the underlying discovery or demo architecture is not yet defined, route that design to `discovery-and-demo-structure` rather than inventing it here.
4. Outline the conversation flow.
Use opener, context, questions, value bridge, proof, and close.
5. Write the actual lines.
Keep the language short, conversational, and specific to the persona and stage.
6. Add proof inserts.
Include short proof points the rep can say naturally without reading a script.
7. Add branch paths.
Cover the likely turns: skepticism, pricing pressure, competitor comparisons, and multi-stakeholder pushback.
8. Add guardrails.
Call out what not to say and where the rep should slow down or ask a question instead.
9. Validate spoken language.
Read the lines aloud when possible. Otherwise apply a breath-unit pass: split long or clause-heavy lines, remove phrases a seller would not naturally say, and keep each turn easy to deliver without reading. For high-stakes rollout, flag the track for rep rehearsal before approval.
10. Add manager checkpoints only when the request includes coaching, inspection, or adoption.
11. Route adjacent work:
   For message strategy, use value-prop-and-positioning.
   For objection playbooks, use objection-library-builder.
   For competitor counters, use battlecard-builder.
   For call coaching, use call-review-coach.
   For adaptive discovery and demo architecture, use discovery-and-demo-structure.

## Output Contract

Always include the role, persona, stage, interaction format, total and available speaking time, beat-level time budget, call objective, next-step ask, executable lines, proof sources, and assumptions.

Add discovery questions, demo checkpoints, commercial or renewal branches, competitor responses, and manager inspection checks only when the selected track or request requires them.

- Proof snippets with source, scope, confidence, and when to deploy them
- Spoken-language validation notes and any rehearsal flag
- Assumptions list when source inputs were incomplete.

## What To Avoid

- Writing polished scripts that sound unnatural in live calls.
- Mixing discovery and demo goals into one unfocused conversation.
- Ignoring role/stage differences and shipping a one-size-fits-all track.
- Treating objection handling as one-line rebuttals without diagnostic questions.

## Quality Bar

- Track sounds like natural speech rather than marketing copy.
- Questions create diagnostic insight, not generic rapport.
- Proof statements are specific and credible.
- Every proof statement is supported by a source or clearly labeled as an assumption that must not be presented as fact.
- Lines pass the spoken-language check and can be delivered without sounding read aloud.
- Role and stage differences are explicit, not cosmetic.
- The next-step ask is concrete and testable.
